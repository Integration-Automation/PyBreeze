# 0002. A run is reported in one schema, the framework's own record kept beside it

- **Status**: Accepted
- **Date**: 2026-10-08
- **Code**: `pybreeze/utils/execution_report/report_schema.py`,
  `test/test_utils/test_execution_report.py`

## Context

Every automation package reports a run in its own way. APITestka, AutoControl, WebRunner and
LoadDensity each write HTML, JSON and XML records of their own (`AT_generate_html`,
`AC_generate_json`, `WR_generate_xml`, `LD_generate_html`, ...), and a pytest file generated by
the importers reports as pytest does. The IDE reads none of them. It shows the child's output as
text and can mail `default_name.html` as it is.

The roadmap's Phase 8 wants one viewer for all of them: a summary, a hierarchy, filters by status,
duration and framework, import and export, and later a comparison of two runs. Phase 7 sends the
results of MCP tool calls into the same model. A viewer that understood each format would be one
viewer per framework, and none of the formats can hold the others.

## Decision

1. **A tree of results under one report.** An `ExecutionReport` is one run of one framework. Its
   `ExecutionResult`s nest, each of a `kind`: suite, test, case or step. A framework uses the
   levels it has.
2. **Four statuses, closed.** `skipped`, `passed`, `failed` (a check did not hold) and `error` (the
   run broke before it could tell). Rolling up takes the most serious.
3. **A framework's verdict on a parent is kept.** A report's status is rolled up from its top-level
   results as they are, not recomputed from their children: a suite whose set-up failed has failed
   although every test under it passed.
4. **A common core, and the rest kept raw.** Status, timing, output, an error, attachments and
   children are typed fields. Whatever else a framework records stays in `raw`, on each result and
   on the report, as JSON-compatible data the viewer can show but does not interpret.
5. **Times are numbers.** `started` is seconds since the epoch, `duration` is seconds, each `None`
   when unknown.
6. **IDs are unique in a report, and stable across runs when made with `stable_id()`.** It hashes
   the parent's ID, the result's name and which of its parent's results of that name it is: nothing
   a run changes.
7. **One written form, checked on the way in.** `to_dict()` writes JSON-compatible data with a
   `schema_version`. `from_dict()` checks every field it knows, names a wrong one by its path,
   leaves an unknown field unread, and refuses a newer version, results nested deeper than 64 and
   two results with one ID.
8. **Immutable and pure.** Frozen dataclasses with tuples; nothing here runs a test or reads a
   framework's file.

## Alternatives considered

- **JUnit XML as the model.** It is the nearest thing to a common format, but it has no level below
  a test case, no attachments, and says status by which child element is present. A browser test's
  steps and a load test's statistics would not fit. It stays a format an adapter can read and write.
- **No schema: pass each framework's own dictionary around.** Every consumer would validate it
  again, each in its own way.
- **Recompute a parent's status from its children.** Simpler to keep consistent, and wrong for a
  suite that failed outside its tests.
- **ISO 8601 strings for times.** Readable in the file, but every filter and sort would parse them,
  and `datetime.fromisoformat` does not read a `Z` suffix on Python 3.10.
- **Random IDs.** Unique, and useless for comparing two runs.
- **A status a framework can extend.** The viewer's filters and colours need a closed set; a
  framework's finer distinction goes in `raw`.

## Consequences

- An adapter that wants its results comparable builds their IDs with `stable_id()`. Two results of
  one name under one parent are told apart by their order, so reordering those changes which is
  which.
- A field that changes meaning raises `SCHEMA_VERSION`. A new optional field does not: an older
  reader leaves it unread.
- The schema carries `stdout`, `stderr` and `raw` as they are given. Whoever builds a result
  removes secrets first: the schema cannot tell a token from a test name. Phase 7 needs this for
  MCP arguments.
- The reasons `from_dict()` refuses a report are tool errors with translations
  (`execution_report_*_error`), ready for the viewer to show.
- No adapter exists yet, so no run is shown in this shape. The adapters, the viewer and the XML and
  HTML import and export are Phase 8.
