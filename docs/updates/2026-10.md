## U-20261001-01 · 2026-10-01 · CI publishes pybreeze_dev from the dev branch · #release #ci #X-13

- **What**: workspace X-13, decided by the owner: the dev channel is published by CI. `pybreeze_dev` had last been uploaded by hand on 2026-04-04 (1.0.14), and no workflow built `dev.toml`.
  - `dev.yml` gets a `publish-dev` job. It runs on a push to `dev` after `unit-tests` passes, never on a pull request or the schedule, on `ubuntu-latest` (building the wheel imports nothing, so it needs no PySide6), and it keeps no checkout credentials. It does not need `sonarcloud`: that job is skipped on a push, and a skipped dependency would skip the upload too.
  - `scripts/dev_release.py prepare` writes `pyproject.toml` from `dev.toml` with the next version: one patch above the newest `X.Y.Z` release on PyPI, or above the version in `dev.toml` when that is higher. Nothing is committed back, so `dev` does not move under the sessions pushing to it; the version in `dev.toml` is a floor.
  - `scripts/dev_release.py changed dist` compares the built wheel with the newest published one, ignoring what only a new version number changes (`RECORD`, `WHEEL`, the `Version:` line). A push that ships nothing new uploads nothing.
  - The job uploads only while its commit is still the tip of `dev`, so a run that finishes after a newer push cannot publish older code as the newest release.
  - The upload uses `secrets.PYPI_API_TOKEN` and installs `build` and `twine` as the `publish` job of `stable.yml` does; trusted publishing and pinning them stay with `progress.md` #54.
